# 설계 문서

## 1. 목표와 비목표

**목표**: 같은 입력이면 항상 같은 상태가 되고(재현성), 장애 상황에서도 포지션·잔고·주문 상태가 실제와 어긋나지 않는(예측 가능성) 매매 시스템.

**비목표**: 전략 수익률. `BreakoutStrategy`는 파이프라인을 돌리기 위한 예시일 뿐입니다.

## 2. 핵심 아키텍처: 이벤트 소싱 + 단일 작성자(single writer)

```
 [시세 피드 A] ─┐
 [시세 피드 B] ─┼─► Sequencer/Queue ─► Engine.on_event() ─► [Command] ─► Exchange 어댑터
 [Clock]       ─┘          │                 │                               │
                           │                 └── 상태: 잔고·포지션·주문·라이프사이클
                           └──► Journal (소비한 순서 그대로) ◄── 체결/ack 이벤트 ◄────┘
```

- **엔진은 순수 상태 기계**입니다. 입력은 이벤트, 출력은 커맨드뿐입니다. `time.time()`, `random`, 네트워크를 엔진 안에서 호출하지 않습니다. "현재 시각"은 이벤트의 `ts`에서만 가져옵니다.
- **상태를 바꾸는 주체는 하나**입니다. 생산자(피드, 타이머)는 여럿이고 비동기지만, 소비자는 하나입니다. 그래서 락이 필요 없고 경쟁 조건이 생기지 않습니다 (LMAX Disruptor와 같은 사고방식).
- **모든 상태는 이벤트 열의 함수**입니다. 저널을 리플레이하면 상태 해시까지 같아집니다.

## 3. 순서 결정론: 두 가지 전략

| 상황 | 방법 | 보장 |
|---|---|---|
| 백테스트, 병렬 처리, 다중 피드 병합 | `Sequencer`: 소스별 seq 빈틈 메우기 + `(ts, source, seq)` k-way 병합 | **어떤 도착 순서여도** 처리 순서가 같습니다 (`test_shuffled_arrival_gives_identical_state`) |
| 라이브 | 단일 소비자 + 저널 | 도착 순서는 실행마다 다를 수 있지만, **소비한 순서를 기록**하므로 언제든 재현할 수 있습니다 |

라이브에서 Sequencer를 쓰지 않는 이유는 워터마크 때문입니다. k-way 병합은 모든 소스의 다음 이벤트가 와야 진행되는데, 조용한 종목 하나가 전체를 멈춥니다. 하트비트(`advance`)로 풀 수 있지만 지연이 생기고, 늦게 도착한 이벤트를 어떻게 처리할지(버릴지, 별도 처리할지)도 정책으로 정해야 합니다. 면접에서 이 트레이드오프를 설명할 수 있으면 됩니다.

**결정론을 깨는 흔한 원인과 대응**

- float 누적 오차 → `Decimal` 강제 (`D(0.1)`은 TypeError)
- dict/set 순회 순서 → 커맨드를 생성하는 순회는 모두 `sorted()`로 처리
- `uuid4()` 주문 ID → `(심볼, 의도, 순번)`으로 결정적으로 만든 ID
- 벽시계 타임아웃 → 이벤트 ts 기준으로 판정 (라이브에서는 Clock 이벤트도 저널에 기록)
- 난수 장애 주입 → seed를 고정하고, 주문당 난수 소비 횟수를 일정하게 유지

## 4. 상태 머신

### 4.1 주문 (`domain/order.py`)

- **타임아웃은 실패가 아닙니다.** ack가 오지 않았다고 재주문하면, 실제로는 첫 주문이 살아 있어 이중 주문이 됩니다. 그래서 `UNKNOWN`으로 두고 `QueryOrder`로 확인합니다.
  - 조회 결과 `NOT_FOUND`이면 거래소에 도달하지 않은 것이므로 REJECTED로 종결합니다. 재주문은 **새 ID**로 합니다.
  - `OPEN`이면 정상으로 복구하고, 이후 주문 타임아웃이 되면 잔량을 취소합니다.
- 체결 통보가 ack보다 먼저 올 수 있으므로 `PENDING_NEW → PARTIALLY_FILLED/FILLED` 전이를 허용합니다.
- **체결은 사실입니다.** 같은 `fill_id`는 한 번만 반영합니다(멱등). 취소 후 늦게 온 체결도 장부에 반영하고 CRITICAL 알림을 보낸 뒤, 라이프사이클을 실제 보유량에 맞게 대사(reconcile)합니다.
- 허용되지 않은 전이가 발생하면 예외를 던지고, 엔진은 신규 진입을 중단(halt)합니다. 조용히 넘기지 않습니다.

### 4.2 포지션 라이프사이클 (`domain/lifecycle.py`)

`FLAT → ENTERING → OPEN → EXITING → COOLDOWN → FLAT`

- ENTERING/EXITING 중에는 새 주문을 낼 수 없습니다. 이것이 중복 주문의 1차 방어선입니다.
- 진입 주문 결과 체결량이 0보다 크면 OPEN, 0이면 FLAT으로 갑니다. 부분 체결만 됐어도 보유량이 있으면 OPEN입니다.
- 청산이 일부만 되면 다시 OPEN으로 돌아가고 `pending_exit_reason`을 유지해, 다음 틱에 잔량 청산을 재시도합니다.
- 쿨다운 길이는 청산 사유별로 다릅니다. STOP 30분, TP·SIGNAL 5분, HALT 무기한입니다.
- 거부되면 `retry_after` 백오프를 걸어 무한 재주문을 막습니다.

## 5. 가격 기준점

| 용도 | 기준 | 위치 |
|---|---|---|
| 사이징 | 주문 지정가 | `RiskManager.size(price=limit)` |
| 손절/익절 | `RiskConfig.stop_ref` (기본 AVG) | `RiskManager.stop_price()` → `Position.ref_price()` |
| 평가·낙폭 | MARK (최신 체결가) | `Engine.equity()` |
| 실현손익 | 이동평균 원가 | `Position.on_fill()` |

규칙: **기준가 계산은 `Position.ref_price()` 한 곳에서만** 합니다. 기준가가 없으면 0을 반환하지 않고 예외를 던집니다.

## 6. 백테스트 함정과 대응

- **봉 내부 경로**: 분봉에는 고가·저가 중 무엇이 먼저였는지 정보가 없습니다. 그래서 롱 전략에 불리한 경로(양봉 O→L→H→C)를 가정합니다.
- **체결 가정**: 지정가와 교차해야 체결되고, 체결 가능량은 시장 체결량 × participation입니다. 체결가는 지정가입니다(보수적).
- **수수료**: 0.05%(업비트 KRW 마켓)를 체결마다 반영합니다.
- **같은 코드 경로**: 백테스트와 라이브가 같은 `Engine`·`Runner`를 사용합니다. 백테스트 전용 분기가 없습니다.

## 7. 알려진 단순화 (다음 단계 후보)

- 업비트 호가 단위는 가격대별로 다르지만, 현재는 `price_tick=1`로 고정되어 있습니다.
- 청산 잔량이 최소 주문금액보다 작은 경우(먼지 잔량) 처리가 없습니다.
- 실거래 어댑터는 비동기 응답이므로 `handle()`이 `[]`를 반환하고, 응답은 별도 소스로 큐에 넣어야 합니다.
- 엔진 상태 스냅샷을 주기적으로 저장하는 기능이 없습니다. 지금은 저널 전체를 리플레이하므로 오래 돌리면 복구가 느려집니다.

## 8. 설명

1. "시스템이 죽는 이유" Top 3: 타임아웃을 실패로 착각해 생기는 이중 주문, 부분 체결 후 상태 불일치, 백테스트와 라이브의 코드 경로 차이. 각각 이 프로젝트에서 어떻게 막았는지.
2. 결정론을 테스트로 증명하는 방법: 상태 해시 + 셔플/동시 생산자 테스트 + 시퀀서 없는 대조군.
3. 라이브에서 순서 재정렬 대신 저널을 택한 트레이드오프 (워터마크 지연 vs 재현성).
4. 늦은 체결을 무시하지 않고 장부에 반영하는 이유: 돈은 이미 움직였기 때문입니다.
